01 · 项目定位与架构目标

开场先讲清“我们为什么这么搭”。后续所有模块的取舍，都服务于下面四个目标。

一句话定位

这是一个面向 电商经营数据问答 的企业级 Text2SQL 智能体：用户用自然语言提问（例如“上个月各品类销售额排名”），系统沿 意图识别 → 证据召回 → Schema 召回 → 规划 → SQL / Python 执行 → 报告生成 的完整链路，最终流式返回图表与结论。

四条核心架构目标（架构师第一性原则）

目标落地手段
可控：LLM 不稳定，流程必须可拆解、可断点、可重放用 StateGraph 图编排替代“单体巨型提示词”，一步一个节点，状态集中管理
安全：直接操作生产业务库SQL 只读白名单校验 + 权限结果脱敏 + Python Docker 沙箱，三层纵深防御
准确：压制 Hallucination 与业务歧义结构化 Schema + 非结构化业务知识双通道 RAG 召回，喂准上下文
协同：Agent 不再是“孤岛”A2A / JSON-RPC 把本 Agent 暴露给外部编排系统；HITL 人工确认应对高风险动作
架构师视角：项目的本质不是“写一个能出 SQL 的聊天框”，而是回答“如何把 LLM 的不确定性装进一个可控、可观测、可演进的工程骨架里”。

这是项目的心脏。先给整体拓扑，再讲节点与边的登记方式。（绿=数据处理，紫=提示词输出，橙=入口/端点）

3.1 全链路拓扑（主路径 + 分支）

图 3-1 · 数据问答 Agent 执行图拓扑（START→意图识别→证据召回→Schema→可行性→规划→执行/report→END；虚线=条件分支；人工确认开关在规划中，本期按需求澄清型 HITL 描述）

3.2 节点与边如何登记（GraphConfiguration）

把 16 个节点注册进图：用 addEdge 串主链、用 addConditionalEdges 做条件路由。

// 意图识别 → 条件路由：data 走证据召回，非 data 走提示词输出
.addConditionalEdges(Graph.Node.INTENT_RECOGNITION,
    AsyncEdgeAction.edge_async(new IntentRecognitionEdge()),
    Map.of(Graph.Node.EVIDENCE_RECALL, Graph.Node.EVIDENCE_RECALL,
           Graph.Node.PROMPT_OUTPUT,    Graph.Node.PROMPT_OUTPUT))

// 可行性评估 → 可行进规划器，不可行直接出报告，或收尾
.addConditionalEdges(Graph.Node.FEASIBILITY_ASSESSMENT,
    AsyncEdgeAction.edge_async(new FeasibilityAssessmentEdge()),
    Map.of(Graph.Node.PLANNER,          Graph.Node.PLANNER,
           Graph.Node.REPORT_GENERATION,Graph.Node.REPORT_GENERATION,
           END,                         END))

// 规划器 → 是否需要人工确认
.addConditionalEdges(Graph.Node.PLANNER,
    AsyncEdgeAction.edge_async(new PostPlannerEdge()),
    new HashMap<String,String>(){{ put(PLAN_EXECUTION, PLAN_EXECUTION);
                                    put(HUMAN_FEEDBACK, HUMAN_FEEDBACK); }})

// 计划执行 → 下一步是 SQL / Python / 收报告 / 结束
.addConditionalEdges(Graph.Node.PLAN_EXECUTION,
    AsyncEdgeAction.edge_async(new PlanExecutorEdge()),
    new HashMap<String,String>(){{ put(SQL_GENERATION,    SQL_GENERATION);
                                    put(PYTHON_GENERATION, PYTHON_GENERATION);
                                    put(REPORT_GENERATION, REPORT_GENERATION);
                                    put(END,               END); }})

// 确定性链路：SQL 生成→执行→回执行器；Python 生成→执行→分析→回执行器
.addEdge(SQL_GENERATION,   SQL_EXECUTION).addEdge(SQL_EXECUTION,  PLAN_EXECUTION)
.addEdge(PYTHON_GENERATION,PYTHON_EXECUTION).addEdge(PYTHON_EXECUTION,PYTHON_ANALYSIS)
.addEdge(PYTHON_ANALYSIS,  PLAN_EXECUTION)
.addEdge(REPORT_GENERATION,END)
.addEdge(PROMPT_OUTPUT,    END);
架构师要点：所有节点都由 TracedNodeAction 包装，用“装饰器”实现“节点执行 + 自动埋点”的横切关注点；State 中每种 Key 登记了 KeyStrategy（如 ReplaceStrategy），保证回环/并发下状态写入语义一致。

04 · 沙箱权限隔离：三道安全防线

数据问答直连业务库，安全是硬约束。按“静态校验 → 结果脱敏 → 运行隔离”三层展开。

4.1 第一道：SQL 静态校验（SqlSecurityValidator）

在真正执行前，用正则做 白名单式 只读校验，从源头掐断注入与写操作。

// 1) 先剥注释，防止 /* */ 绕过
String normalized = COMMENT.matcher(sql).replaceAll(" ");
// 2) 去掉字符串字面量后再按分号计数，防多语句注入
String noStrings = stripStrings(normalized);
if (countTopLevelSemicolons(noStrings) > 1)
    return Result.deny("检测到多条语句，禁止批量执行（防止注入）。");
// 3) 必须以 SELECT 或 WITH...SELECT 开头（白名单入口）
if (!SELECT_HEAD.matcher(normalized).find())
    return Result.deny("仅允许 SELECT 只读查询，当前 SQL 不是 SELECT。");
// 4) 禁用 drop/alter/delete/update/insert/truncate/merge/exec/
//    pragma/attach/detach/vacuum/create/grant/revoke…
if (FORBIDDEN.matcher(noStrings).find())
    return Result.deny("SQL 包含禁用关键字（仅允许 SELECT 只读查询）。");

SqlSecurityValidator.validate()

4.2 第二道：权限拦截与结果脱敏（PermissionInterceptor）

  • 运营 OPERATOR仅可访问所属店铺，禁止跨店；敏感字段脱敏
  • 客服坐席 AGENT仅可查单个买家，不支持批量导出；手机号/地址脱敏
  • 管理员 ADMIN全量访问，但敏感列仍脱敏
// 敏感列命中即打码（手机号保留前3后4，地址打码）
private static final Set<String> SENSITIVE_COLUMNS = Set.of(
    "phone","mobile","tel","address","身份证","手机号","收货地址","联系电话");

// SQL 执行节点出口统一调用脱敏，再交给报告
resultSetWrapper = permissionInterceptor.mask(resultSetWrapper);
架构师要点：校验与脱敏不是散落各节点，而是收敛到“SQL 执行节点出口”这一唯一边界，形成可审计的安全闸门，后续无论 SQL 还是 Python 结果都统一过闸。

4.3 第三道：Python 运行沙箱（SimplePythonExecutor → Docker）

Python 代码等价于“任意程序”，必须放进一次性、无网络的容器。

docker run --rm -i \
  --network none              # 完全断网
  --cpus 1                    # 限制 1 核
  --memory 512m               # 内存上限（DATA_AGENT_PYTHON_MEMORY_LIMIT 可调）
  --pids-limit 128            # 进程数上限，防 fork 炸弹
  --security-opt no-new-privileges  # 禁止提权
  -v workDir:/work:ro         # 只读挂载输入
  -w /work data-agent-python:latest python /work/script.py
// 超时强杀：防止死循环拖垮 JVM
Process process = new ProcessBuilder(command).redirectInput(inputFile).start();
boolean completed = process.waitFor(timeoutSec, TimeUnit.SECONDS);
if (!completed) { process.destroyForcibly();
    return new PythonExecutionResult(false, "", "Execution timed out after ... seconds."); }
踩坑复盘：沙箱报 docker: error during connect ... Access is denied 是 Docker daemon 未就绪或权限不足，并非业务逻辑问题。恢复“启动 Docker + 镜像可用”即恢复；因而执行前用 isDockerAvailable() 前置探测，给出更友好报错。

05 · 意图识别：前置分流

不是所有请求都值得走沉重 NL2SQL。第一步先用 LLM + 轻量规则，把问候/闲聊/无关挡在门外。

5.1 判断逻辑（IntentRecognitionNode）

out.put(Intent.CLASSIFICATION, classification);
out.put(Intent.TYPE, detectType(userInput, classification));  // 落到三类
return out;

// 规则兜底：问候词命中或模型判“问候/打招呼”→ greeting
static String detectType(String userInput, String classification) {
    if (isGreeting(u) || c.contains("问候") || c.contains("打招呼"))
        return Intent.GREETING;
    if (c.contains("闲聊") || c.contains("无关") || c.contains("聊天"))
        return Intent.CHAT;
    return Intent.DATA;   // 其余全部视为数据问答
}

INTENT_TYPE ∈ { greeting, chat, data }

return Graph.Node.PROMPT_OUTPUT;

问候 → 直接 Flux 输出配置好的开场白；闲聊/无关 → 按人设提示词交大模型流式直答，不再碰数据库。

06 · 证据召回与 Schema：双重检索

Text2SQL 的准确率，很大程度取决于“喂给 LLM 的上下文对不对”。这里采用非结构化知识 + 结构化 Schema双通道并举。

6.1 证据召回（EvidenceRecallNode）

  • 查询改写：先用 LLM 把“多轮口语”改写为独立检索查询（rewrite）
  • 业务词条/知识（glossary）：术语口径解释
  • 问答对知识（QuestionKnowledge）：历史“问题→SQL+答案”参考
  • 汇总成 EVIDENCE 提示词，供可行性评估与规划器消费
// 改写为独立检索查询
EvidenceQueryRewriteResult convert =
    new BeanOutputConverter<>(EvidenceQueryRewriteResult.class).convert(rewriteResponse);
String rewriteQuery = convert.getStandaloneQuery();

// 双通道召回（VectorStore + databaseId 元数据过滤）
List<Document> glossaryKnowledge = retrieveGlossary(rewriteQuery, databaseId);
List<Document> knowledgeDocs    = retrieveKnowledge(rewriteQuery, databaseId);
List<QuestionKnowledge> qkList  = questionKnowledgeMapper.findByIds(...);

EvidenceRecallNode.apply()

6.2 Schema 召回（SchemeReCallNode）

表结构是动态的，因此把「表、字段」描述向量化，按查询相似度召回候选并过滤当前库：

// 表级：topK=10，过滤库内 TABLE 类型向量
SearchRequest tableReq = SearchRequest.builder().query(rewriteQuery)
    .filterExpression(b.and(b.eq(VECTOR_TYPE, TABLE),
                            b.eq(DATABASE_ID, databaseId)).build())
    .topK(10).build();

// 列级：topK=30，过滤 COLUMN 类型向量
SearchRequest columnReq = SearchRequest.builder().query(rewriteQuery)
    .filterExpression(b.and(b.eq(VECTOR_TYPE, COLUMN),
                            b.eq(DATABASE_ID, databaseId)).build())
    .topK(30).build();

SchemeReCallNode.retrieveTable / retrieveColumn

架构师要点：vector_type + database_id 双元数据过滤是多库隔离的根基，避免跨库串场。Schema.buildSchemePrompt() 把召回到的表/列/关系统一渲染成 LLM 可读的 Schema 提示。

6.3 表关系 + 可行性评估

  • TableRelationNode：补充外键 / 关联关系（前端展示“外键 ?.?→?.?”的乱码，是数据侧表名列未填充导致，需把真实列名回填）
  • FeasibilityAssessmentNode：拿召回 Schema + Evidence 判断“能不能答、缺不缺表”；不可行 → 直接跳报告生成解释，可行 → 规划器

07 · 规划器与执行：NL2SQL 的核心

规划器把“召回结果”变成多步、可执行、可自纠错的计划，再由执行器逐条驱动 SQL / Python。

7.1 Plan 数据模型

class Plan {
    @JsonProperty("thought_process") String thoughtProcess;    // 分析思路
    @JsonProperty("execution_plan") List<PlanStep> executionPlan; // 步骤列表
}
class PlanStep {
    int  step;
    @JsonProperty("tool_to_use")   String toolToUse;   // SQL_GENERATE / PYTHON_GENERATE / REPORT…
    @JsonProperty("tool_parameters") ToolParameters toolParameters; // 指令 / 建议 / sql_query
}

7.2 退化计划兜底重规划（PlannerNode）

聚合/汇总/历史类问题若被压成 ≤1 条原始 SQL，答案必然残缺。规划器内置重规划回路：

int attempt = 0;
while (true) {
    args.put("plan_validation_error", validationFeedback);
    plan = callLLM(plannerPrompt, args);
    Plan parsed = parse(plan);
    if (isDegeneratePlan(rewriteQuery, parsed) && attempt < MAX_REPLAN) {
        attempt++;
        validationFeedback = "上次计划过简（<=1 条 SQL），无法覆盖聚合/汇总/历史类问题。"
            + "请先分步查询订单/退款明细，再做聚合汇总(SUM/COUNT/GROUP BY)，"
            + "必要时追加 PYTHON_GENERATE_NODE。";
        continue;   // 携反馈重新规划
    }
    break;
}

“过简计划检测 + 携反馈重规划”自纠错

7.3 计划执行器与闭环（PlanExecuteNode / PlanExecutorEdge）

PLAN_EXECUTE 作为调度中枢，读取当前 CURRENT_STEP，按 tool_to_use 决定下一跳：

图 7-1 · PLAN_EXECUTE 调度中枢：按 tool_to_use 条件分发，执行结果回传形成闭环自纠错

String tool = Plan.getCurrentStep(state).getToolToUse();
switch (tool) {
    case SQL_GENERATION:    return SQL_GENERATION;
    case PYTHON_GENERATION: return PYTHON_GENERATION;
    case REPORT_GENERATION: return REPORT_GENERATION;
    default:                return END;
}
架构师要点：执行失败会记录进 EXECUTION_OUTPUT，并在下一步携带“失败反馈”重新生成，形成闭环自纠错；CURRENT_STEP 作为游标，支持多步计划与断点续跑语义。SQL 执行节点里再次调用 SqlSecurityValidator + PermissionInterceptor，等于沙箱校验其实贯通了“生成 → 执行”全链路。

08 · 报告生成与流式前端

// 且连接超 20s 无新事件 → 自动标记已完成，双保险杜绝“卡报告生成中”

8.2 简洁 / 复杂双模式（前端 DataChat）

模式UI 定位展示内容
复杂模式过程透明、可审计每个节点执行过程、SQL、中间结果、图与结论
简洁模式只关心答案仅展示「处理流程」缩略提示 + 最终报告，不铺开细节

踩坑复盘（你多次反馈）：报告明明生成但页面仍卡“报告生成中”。根因是流式终端状态未送达。修复 = 后端 onComplete() 必须显式 taskUpdater.complete() 发出 status-update.completed；前端再加 20s 空闲兜底收尾，双保险彻底解决。

10 · 可观测性与追踪

图编排最大的收益之一，就是“每一个节点都可被记录、回放、断点”——这也是调试中心的数据来源。

  • TraceFrame：一次节点执行的输入/输出/耗时/状态
  • TraceTask：一次问答任务的完整轨迹（多帧有序串联）
  • TracedNodeAction：包装每个节点自动埋点，taskTraceService 负责落盘/查询
  • 调试中心（前端 /debug）：查看任务帧、节点状态机“运行中/完成”
// 节点执行与埋点解耦：任何节点包一层即自动被追踪
TracedNodeAction(action = AsyncNodeAction.node_async(sqlGenerateNode),
                 nodeName = SQL_GENERATION,
                 traceService = taskTraceService);
架构师要点：“可观测”是生产级 Agent 的刚需。A2A 的 stateTransitionHistory 能力与其一脉相承——外部调用方可回看整条状态转移历史。

12 · 架构评审与演进路线

架构成立之处（优点）

  • 流程可演化：加节点/边是“配置式”改动；意图前置、HITL、退化解重规划都是这样一步步演化出来的
  • 安全分层：静态校验 + 权限脱敏 + 运行沙箱三道独立防线，纵深防御
  • 召回双通道：结构化 Schema 与业务知识互补，是准确率主引擎
  • 标准互通：A2A / JSON-RPC 让 Agent 可被编排，而非“孤岛应用”
  • 可观测到帧：Trace 贯穿每一步，调试与生产定位都受益

待优化 / 演进建议

  • 检索耗时优化：证据召回一次包含多次 LLM 调用 + 向量检索，可加缓存 / 并发化 / 向量索引调优，或按意图跳过非必要召回
  • agent_config 目前单实例全局配置，演进方向是按库 / 按租户隔离
  • Python 沙箱建议补充磁盘配额、seccomp syscall 白名单、镜像签名，进一步收敛攻击面
  • 报告生成尽量用schema 白名单校验 ECharts JSON，防止脏数据与注入
  • A2A 面向内网学习场景，生产需补鉴权（AuthN/Z）

一句话总结

这是一个“把 LLM 的不确定性装进可控编排里”的样本工程：用 StateGraph 固化流程、用双通道召回喂准上下文、用三层沙箱守住安全、用 A2A 打开互通，最终在可控、安全、准确、效率四个维度取得工程化平衡。

13 · Query 改写：让检索听懂人话

证据召回的“隐形第一站”——把多轮对话中的代词、省略句、寒暄噪声，重写为一条独立完整的陈述句（standalone_query），一次改写、全链路复用。

13.1 为什么需要改写

向量检索做的是“语义匹配”，它假设输入是一条语义自足（self-contained）的查询。但真实的多轮对话完全不是这样：

原始输入直接检索的问题改写后（standalone_query）
“那华北呢？”只剩“华北”字面相似，丢失“查销售额”这个动作“查询华北地区的销售额”
“它的销量怎么样”代词“它”没有 embedding 意义，召回随机漂移“A 产品的销量如何”
“嗨，那个，我想知道咱们核心用户的定义到底是啥呀”寒暄噪声稀释关键词权重“查询核心用户的定义”
架构判断：改写被放在召回链路最前端（证据召回节点内部的第一步）而非独立图节点——它没有分支语义、是必经一步；但它持有独立提示词与输出契约，职责被清晰剥离，可单独调优。

13.2 三条改写原则（业务规则即提示词）

多轮上下文 + 最新输入
→
① 指代消解
→
② 上下文补全
→
③ 去噪精简
→
standalone_query
  • 指代消解：代词（它 / 这个 / 那个）必须还原为具体业务名词：“那个的销量如何” → “A 产品的销量如何”
  • 上下文补全：追问省略主语谓语时补全：“销售部呢？” → “查询销售部的花费情况”
  • 去噪精简：剔除“你好 / 请问 / 麻烦”等礼貌语与情绪助词；若开启全新话题则忽略历史直接重写

提示词全文见 resources/prompts/evidence-query-rewrite.st，内置 4 组 few-shot 示例覆盖指代、补全、去噪、话题转换四种情形。

13.3 实现：强约束 JSON 输出契约

改写结果只允许一个字段——standalone_query。通过 BeanOutputConverter 把 Bean 上的 Jackson 注解渲染成 format 指令注入提示词，模型输出再直接反序列化回对象，杜绝自由文本漂移：

public class EvidenceQueryRewriteResult {
    @JsonPropertyDescription("重写后的完整句子")
    @JsonProperty("standalone_query")
    private String standaloneQuery = "";
}
// EvidenceRecallNode.apply() 第一步：渲染改写提示词并调用 LLM
BeanOutputConverter<EvidenceQueryRewriteResult> converter =
        new BeanOutputConverter<>(EvidenceQueryRewriteResult.class);
Map<String, Object> args = new HashMap<>();
args.put("latest_query", userInput);            // 最新一句
args.put("multi_turn",   multiTurn);            // 多轮上下文
args.put("format",       converter.getFormat());// 注入 JSON 输出契约
String prompt = promptManager.getEvidenceQueryRewritePromptTemplate().render(args);
String response = ChatClient.create(chatModel).prompt()
        .options(OpenAiChatOptions.builder()
            .extraBody(Map.of("enable_thinking", false)).build()) // 关闭思考链压低延迟
        .user(prompt).call().content();
String rewriteQuery = converter.convert(response).getStandaloneQuery();
工程细节：enable_thinking=false 显式关闭推理模型的思考链——改写是每次问答都走的“快路径”，必须压到亚秒级；返回为空时直接抛错，宁可失败也不拿脏查询去检索。

13.4 一次改写，全链路复用

改写结果写入状态键 Recall.REWRITE_QUERY，成为整条链路的“标准查询”（canonical query），后续环节全部消费它而不是原始输入：

架构收益：语义在入口处归一化之后，下游每个节点都不需要再各自理解“它 / 那个 / 呢”，提示词全部围绕单一 canonical query 设计——这是减少 NL2SQL 长链路提示词漂移、保证各节点理解一致的关键手段。

14 · 节点实现逻辑全解

按拓扑顺序逐一拆解 15 个业务节点：类型、输入 → 输出、实现要点、关键代码。所有节点都只是 NodeAction.apply(OverAllState) → Map<String, Object>——读状态、做一件事、把结果增量写回状态。

14.1 前置分流：意图识别 → 提示词输出

意图识别 IntentRecognitionNode LLM

  • 职责：在证据召回之前挡住非数据请求——问候 / 闲聊 / 无关指令不进入 NL2SQL 链路，直接交给提示词输出节点，省去全部检索与规划开销。
  • 双保险设计：LLM 输出 IntentClassificationResult.classification 之外，本地词表兜底——命中“你好 / 在吗 / hello”等直接判 greeting，避免模型抖动把“你好”误判为数据问题；JSON 解析失败时回退用原始响应文本做 contains 判定。
static String detectType(String userInput, String classification) {
    if (isGreeting(u) || c.contains("问候") || c.contains("打招呼")) return GREETING;
    if (c.contains("闲聊") || c.contains("无关") || c.contains("聊天")) return CHAT;
    return DATA;   // 其余一律走数据链路
}

提示词输出 PromptOutputNode 流式 LLM

  • 职责：承接被意图识别拦下来的请求。问候→直接返回配置的开场白；闲聊 / 无关→套上配置的人设提示词流式回复。
  • 配置驱动：开场白与人设都来自 agent_config（智能助手配置页可改），缺省时回落到内置的「小鑫」默认值；闲聊回复把多轮上下文拼进 user 消息，保持对话连贯。
  • 流式契约：问候不消耗 LLM——Flux.just 单帧直接返回；闲聊用 .stream().chatResponse()，且包一层 withIdleCompletion(30s)：模型空闲超时立即 complete，保证前端气泡一定收尾。
if (GREETING.equals(type)) {
    out.put(REPORT_RESULT, plainFlux(opening));       // 开场白：单帧，不调 LLM
} else {
    out.put(REPORT_RESULT, chatFlux(persona, userInput, multiTurn)); // 人设闲聊：流式
}

14.2 召回链路：证据召回 → Schema 召回 → 表关系

证据召回 EvidenceRecallNode LLM + 向量

  • 第一步先做 Query 改写（完整拆解见第 13 章），得到 REWRITE_QUERY 后才进入检索。
  • 双通道检索：术语知识（GLOSSARY_KNOWLEDGE，topK 4）+ 问答知识（QUESTION_KNOWLEDGE，topK 4），均按 databaseId 做元数据过滤，实现按库隔离。
  • 回表拼装：命中的问答知识按 KNOWLEDGE_ID 回 MySQL 查出完整的「来源 + Q + A」文本，与术语文本一起拼成 EVIDENCE，作为规划与 SQL 生成的业务先验。
SearchRequest req = SearchRequest.builder().query(rewriteQuery)
    .filterExpression(b.and(
        b.eq(VECTOR_TYPE, QUESTION_KNOWLEDGE),
        b.eq(DATABASE_ID, databaseId)).build())   // 类型 + 租户双过滤
    .topK(4).build();
return vectorStore.similaritySearch(req);

Schema 召回 SchemeReCallNode 向量

  • 职责：用同一个 REWRITE_QUERY 召回结构化元数据——表描述 topK 10、列描述 topK 30。
  • 产出：TABLE_SCHEMA / COLUMN_SCHEMA 两组 Document（元数据带 TABLE_ID / COLUMN_ID / 相似度 score），是表关系节点做打分与裁剪的原料。
  • 为什么列召得比表多：列是 JOIN 与筛选条件的主要载体，宽表场景下需要更大候选池兜底；最终保留哪些列由表关系节点裁剪决定。

表关系 TableRelationNode 向量 + DB + LLM

  • 四步流水线：① 按 score 给表 / 列打分（同表取 max）→ ② 阈值选表（基线 0.4，目标约 4 张）→ ③ 外键扩散：命中表的一跳外键全部纳入，外键两端列强制保留（前端“表关系 / 外键”卡片的数据就来自这里）→ ④ mix-selector LLM 二次筛表，剔除弱相关表。
  • 设计动机：纯向量召回只看语义相似，会漏掉“语义不像但 JOIN 需要”的桥接表；外键扩散用数据库的强结构把拓扑补回来，向量 + 拓扑 + LLM 三票制显著降低漏表率。
  • 产出：TABLE_RELATION（finalSchema JSON：最终表集合 + 全列定义 + 外键视图）。

14.3 评估与规划：可行性评估 → 规划器 → 人工确认 → 计划执行

可行性评估 FeasibilityAssessmentNode LLM

  • 职责：把 Schema、证据、canonical query、多轮上下文一起喂给评估提示词，判定该问题“能用现有数据回答 / 需要澄清口径 / 只是业务咨询”。
  • 与下游的约定：输出文本中含“需要澄清 / 需求澄清”标记时，报告生成节点会短路——不走 LLM 报告，而是把澄清问题直接抛回给用户追问（见 14.5）。

规划器 PlannerNode LLM

  • 职责：把需求拆成步骤化计划 Plan（每步 = 工具 + 参数 instruction），同样用 BeanOutputConverter 强约束输出 JSON。
  • 退化计划检测：问题命中“历史 / 汇总 / 统计 / GMV / 销售额…”等聚合关键词，却只生出 ≤1 条可执行步骤时判定为退化——携带明确反馈重规划一次（MAX_REPLAN=1），避免“一条原始 SELECT 直接出报告”的残缺答案。
  • 人工反馈回路：人工确认驳回时，反馈内容注入 plan_validation_error 一并渲染进提示词，带着“上次为什么不行”重新规划。
if (isDegeneratePlan(rewriteQuery, parsed) && attempt < MAX_REPLAN) {
    attempt++;
    validationFeedback = "上次计划过简（<=1 条 SQL），无法覆盖聚合/汇总类问题。"
        + "请拆分多步：先查明细，再聚合（SUM/COUNT/GROUP BY）…";
    continue;   // 携带反馈重规划一次
}

人工确认 HumanFeedbackNode 编排

  • HITL 总开关：开关关闭（默认）→ 直接放行 PLAN_EXECUTION，全自动跑完；开启 → 强制停在确认点等待人工。
  • 熔断：REPAIR_COUNT ≥ 3 不再纠缠，路由到 END 终止，防止“确认-驳回-重规划”死循环。
  • 三路分流：批准 → PLAN_EXECUTION；驳回 → PLANNER 且回填反馈 + 修复计数 +1。
if (!hitlEnabled)            return next(PLAN_EXECUTION);  // 开关关：全自动
if (repairCount >= 3)        return next(StateGraph.END); // 熔断
if (approved)                return next(PLAN_EXECUTION);  // 批准：放行
return next(PLANNER, feedback, repairCount + 1);           // 驳回：带反馈重规划

计划执行 PlanExecuteNode 编排

  • 纯调度器：不调用 LLM、不碰数据——按 CURRENT_STEP 把 NEXT_NODE 指向计划里当前步骤的 toolToUse。
  • 收尾判定：步骤全部执行完时，若最后一步本身是报告节点则直达 END，否则补挂一次报告生成——保证任何计划都以报告收场。
if (currentStep > steps.size()) {
    next = lastIsReport ? StateGraph.END : REPORT_GENERATION;  // 保底出报告
} else {
    next = steps.get(currentStep - 1).getToolToUse();          // 调度到工具节点
}

14.4 执行链路：SQL 生成 → SQL 执行 → Python 三连

SQL 生成 SqlGeneratorNode LLM

  • 职责：取当前步骤的 instruction（规划器给这一步的自然语言任务）+ Schema + 证据，生成指定方言的只读 SQL。
  • 三重清洗 extractSql：① 剥掉 markdown 代码围栏 → ② 正则定位首个 select|with 关键词，丢弃前面的模型碎碎念 → ③ 截断到最后一个分号，丢弃尾部解释——把 LLM 的自由输出收敛为可执行 SQL。
private static final Pattern SQL_START = Pattern.compile("(?is)\\b(select|with)\\b");
// 围栏剥离 → 定位 SELECT/WITH → 截断到最后一个分号
Matcher m = SQL_START.matcher(s);
if (m.find()) s = s.substring(m.start());
int lastSemi = s.lastIndexOf(';');
if (lastSemi >= 0) s = s.substring(0, lastSemi + 1);

SQL 执行 SqlExecuteNode 执行 + 安全

  • 三道工序：SqlSecurityValidator.validate 静态安全校验（仅 SELECT、禁 DDL/DML、防全表扫描）→ PreparedStatement 预编译执行（参数化防注入）→ permissionInterceptor.mask 对敏感列做数据脱敏后出池。
  • 失败不炸图：校验失败 / 执行异常都写入 step_n 的 error 结果并照常 CURRENT_STEP+1，让后续步骤与报告能看到“哪一步、为什么挂了”，而不是整个图抛异常中断。
  • 展示规格：结果集同时生成 DisplaySpec（默认 table 视图，首列 x 轴、其余 y 轴），前端表格 / 图表直接消费。

Python 生成 PythonGeneratorNode LLM

  • 职责：为分析型步骤生成可执行 Python 脚本。
  • 以真实数据为样本：把上一步 SQL 查询结果集 JSON 直接作为 sample_input 注入提示词，脚本按真实字段与值域编写——大幅降低“字段名脑补”导致的运行期 Key 错误。

Python 执行 PythonExecuteNode 执行 + 沙箱

  • 职责：SimplePythonExecutor.execute(code, inputJson)——把脚本与输入数据投递进 Docker 沙箱镜像 data-agent-python 执行，网络与资源受限（详见第 04 章三道防线）。
  • 契约：输入必须是上一步 SQL 结果集 JSON（为空直接抛错），输出原样回写 PYTHON_EXECUTION_RESULT。

Python 分析 PythonAnalyzeNode LLM

  • 职责：把脚本的结构化输出（聚合结果 / 异常栈）对照用户原始问题，解读成自然语言结论。
  • 落点：结论写入 step_n_analysis——报告生成节点拼装素材时会优先引用它，让最终报告“说人话”而不是堆 JSON。

14.5 报告生成 ReportGeneratorNode

报告生成 ReportGeneratorNode 流式 LLM

  • 澄清短路：可行性结果含“需要澄清”时，抽取其中的澄清问题，包装成友好追问文本单帧返回——绕过 LLM 报告、绕过一切执行结果拼装，直接 END。这是“需澄清”分支不产生空报告的保证。
  • 素材拼装：原始需求 + 计划思考过程 + 每个步骤的工具 / SQL / 结果集 / Python 分析结论，渲染 report-generator-plain.st（内置 ECharts cleanJsonExample 引导模型产出可直接渲染的图表 JSON）。
  • 回答模式注入：answer_mode（concise / detail）作为模板变量进入提示词——前端“简洁 / 复杂”模式的文案风格分叉点就这里，而过程细节的折叠则由前端按模式控制。
  • 流式收口：withIdleCompletion(20s)：模型一旦空闲超时立即 complete——这是治理“报告生成中…”卡住的关键兜底，前端气泡无论如何都会收尾退出加载态。
// 需澄清：不过 LLM，单帧追问直接返回
if (feasibilityResult.contains("需要澄清") || feasibilityResult.contains("需求澄清")) {
    return buildClarifyResponse(feasibilityResult);
}
// 正常路径：流式 + 空闲收口
return stream.timeout(Duration.ofSeconds(20))
             .onErrorResume(TimeoutException.class, e -> Flux.empty());
回看全局：15 个节点共享同一份极简契约（读状态 → 返回增量 Map），差异只在于“那一件事”是什么——LLM 调用、向量检索、DB 执行、沙箱运行，还是纯路由。也正是这份契约，让意图前置、HITL、退化重规划这些能力都能以“加节点 / 加条件边”的方式后来居上，而不需要重写主干。
